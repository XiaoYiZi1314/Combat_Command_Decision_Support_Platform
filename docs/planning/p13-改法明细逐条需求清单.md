## 一、水源档案（1.1 – 1.9，9 项）

### 1.1 水源卡片补全字段
- **改哪里**：水源档案列表卡片 + 新建/编辑表单。
- **现状**：表 `ccds_water_source` 初版 12 列（`0004_water/0001_water.sql:2-19`）；11 个结构化列**已在 0009 批次建好**（`0009_legacy_seed/0002_water_fields.sql:10-20`：setup/pipe_diameter/pressure_mpa/flow_lps/supply_form/add_height_m/usable/reason_text/reason_code/part_code/is_repair），但 `WaterSourceDO.java:26-81`、`WaterSaveCommand.java:34-78`、`WaterVO.java`、`WaterSourceMapper.xml`（resultMap / WaterColumns / insert / insertBatch / update **5 处**）、`WaterViewTranslator.java:32-46` **全部没接**；前端表单只有 7 个控件（`water/index.js:486-494`）。
- **怎么改**：
  1. 打通 11 列：DO / Command / VO / Mapper 5 处 / Translator 全链路补字段 + `*Label` 中文展示。
  2. 编辑表单按顺序追加：设置方式（地上/地下）、管网直径 mm、管网压力 MPa、管网流量 L/s、给水形式（环状/枝状）、加水高度 m。
  3. 加「不好用原因」九项单选（无水/漏水/压力不足/锈蚀/埋压/圈占/毁坏/挪用/塌井），一卡只记一个主原因。
  4. 加「部件损坏」八项单选（管网/井盖/出水口闷盖/闸阀/放水阀/上水阀/出水口/标志牌）。
  5. 加「可使用（是/否）」「是报修（是则填原因）」「备注」。
  6. 列表卡片：不好用的卡在名称下直接写「原因 · 部件 · 备注」，不再只显示一个「报修」（现 `water/index.js:386-438` 无此行）。
  7. **类型归一修正**：现 `WaterTypeEnum.fromLabel:100-102` 对「含消火栓且不含地下」直接判地上，导致「类别=消火栓 + 设置方式=地下」被导成**地上**，直接打乱 326/7 口径。改为 setup 优先，抽 `WaterTypeResolver` 纯函数供 CRUD 与导入共用。
- **验收**：任意一条水鹤/消火栓，编辑页能填完上述字段，保存后回读内容仍在。
- **依赖**：无。**需额外确认**：D8（兜底原因）。

### 1.2 不好用的判定口径
- **改哪里**：列表筛选、卡片颜色、汇总数字、导出表。
- **现状**：只有 `active/repair` 两态（`WaterStatusEnum.java:14,19`）；无「不好用」谓词；筛选直接比 `water.status`（`water/index.js:349`）；汇总只数 status（`water/index.js:365-366`）。
- **怎么改**：新增 `WaterStatusResolver` 纯函数，**唯一谓词**：
  - `bad := status='repair' OR usable='bad' OR is_repair=1`
  - `good := status='active' AND usable IS DISTINCT FROM 'bad'`
  - **严禁让 `reason_text` 非空参与判定**（旧原因文本不得计入）。
  - 保存时服务端派生 `status`（bad→repair，否则 active）；前端撤掉「状态」控件只留「可使用/是否报修」，杜绝矛盾值。
  - 筛选「报修」= bad 集合；筛选「在用」不含 bad；地图 marker、nearby SQL、汇总、导出全部改调同一谓词；`selectActiveAll` 的 `status='active'` 改为「非 bad」。
  - **禁止用旧审批记录/出水视频回写状态**。
- **验收**：`active+good+is_repair=0` 且备注留有旧原因 → 不计不好用；`repair` → 计入；筛选结果集与 SQL 谓词集合逐 id 相等；导出与界面逐行一致。
- **依赖**：1.1。**需额外确认**：好用卡是否清空备注原文（保存 vs 展示两件事）。

### 1.3 原因文字归到九个原因格
- **改哪里**：导入检查表、汇总原因列、明细原因勾。
- **现状**：零实现（`reason_code`/`part_code` 列空置，旧数据迁移脚本里有 SQL 侧归类但 Java 侧无）。
- **怎么改**：新增 `WaterReasonEnum`（9 值，**方法内顺序即优先级**，兜底 DAMAGED）+ `WaterPartEnum`（8 值，兜底闸阀）+ `WaterReasonClassifier` 纯函数（无 Spring/无 DB）：
  - 原因顺序：无水（无水/没水/管网内没/管道无水/管网无）→ 漏水（漏/锁不住水）→ 压力不足（压力）→ 锈蚀（锈/绣）→ 埋压（埋压/被埋）→ 圈占（圈占/围挡）→ 挪用 → 塌井（塌井/井塌）→ 兜底毁坏。
  - 部件顺序：井盖 → 闷盖 → 放水阀 → 上水阀/开水阀 → 标志牌 → 出水口 → 闸阀（闸阀/阀门/锁芯/扳手/转换器/开关）→ 管网（管网/管道/水管）→ 兜底闸阀。
  - 例：「阀门损坏导致水压不足」→ 原因压力不足 + 部件闸阀。
  - **仅在 bad 为真时归类并写码；good 时强制清空**；`reasonCode` 不接受前端传，服务端重算；`reason_text` 保留原文以支持 1.4 往返。
- **验收**：「管网内没水」「锁不住水」「水压不足」三条备注分别落无水/漏水/压力不足。
- **依赖**：1.2。

### 1.4 检查表导入按全市明细的列来
- **改哪里**：导入表格 + 导出模板。
- **现状**：导出仅 **9 列**（`WaterSpreadsheetSupport.java:33-35`），导入表头定位带**硬编码 fallback 下标 1/3/4/10/12/14/15/16**（`WaterServiceImpl.java:324-331`，恰是旧版 17 列坐标）；`applyImportRows:322-408` **只 INSERT、按 name 判重、不 UPDATE**；行数上限 500（`WaterRuleConstant.IMPORT_MAX_ROWS`）→ 643 条整表会被直接拒收；**模板接口 100% 失败**（`WaterController.java:196` 用 `getWater(stationId, 0L)` 做权限校验，必抛 WATER_NOT_FOUND）；导出缺「序号」列，导出→导入会生成「类别 类别」式错名并撞 `uk_water_station_name`。
- **怎么改**：
  1. 模板 23 列按序：序号、类别、辖区队站、设置方式、地理位置、管网直径 mm、管网压力 Mpa、管网流量 L/S、给水形式、加水高度 m、使用状态（好用/不好用）、无法出水原因、是否报修、水源照片、备注、经度、纬度、泄水阀、泄水阀好用情况、无法查看泄水阀原因、泄水阀备注、是否有保暖措施、无保暖措施原因。
  2. 导入三步：预取本站全量建「辖区队站+地理位置 → DO」内存索引（避免 N+1）→ 逐行解析 23 列 → 命中 `update` / 未命中 `insert`；**删掉所有 fallback 硬编码下标**。
  3. 使用状态=好用 → status 在用、usable 好用，清空原因勾/部件勾/是报修/备注；=不好用 → status 报修、usable 不好用、是报修=是，原因按 1.3 归类打勾。
  4. **只填泄水阀/保暖两段、未改使用状态的行**：只更新这 6 列，**不动在用/报修**。
  5. 导出模板与导出数据同一套列；导出→再导入，条数与状态不变。
  6. 上限 500 → 2000；逐行 update 改批量；顺修模板接口与「序号」列。
- **验收**：模板可下载；整表导入后 `GROUP BY type` 与客户明细一致；打乱行序导入后业务字段与 id 集合不变（证明未按行号覆盖）；往返逐单元格 diff=0。
- **依赖**：1.1 / 1.2 / 1.3。**需额外确认**：D3、D6。

### 1.5 照片和出水视频
- **改哪里**：水源卡片照片、出水视频按钮。

- **怎么改**：新增壳能力 `capturePhoto` / `recordVideo(EXTRA_DURATION_LIMIT=10)` / `probeVideo`（读时长 + 抽 0/50%/100% 三帧）+ H5 `lib/media.js`；服务端新表 `ccds_water_video`（water_id/file_id/duration_ms/frame_file_ids/check_status/check_reason）+ `ModelGateway.completeVision` 逐帧判定 passed/rejected/failed，rejected 必带原因；统计口径「`status='active'` 且存在视频」，报修卡不计；同步/更新目录时本地照片视频不被无视频目录冲掉；列表封面**批量取**（一次 `selectByBizTypesAndIds` + 批量预签名），下线列表期逐文件 COS HEAD。
- **验收**：在用卡传 10 秒内视频 → 计数 +1；超 10 秒被拒且原视频还在；报修卡有视频不计数。
- **风险**：客户端上报不可独立验证 → 落库标 `client_reported`，文案写「辅助判断」；视频含人员/涉密标识 → 私有桶 + 短时 URL；鸿蒙先降级「不支持拍摄，请从相册选择」。
- **依赖**：1.1。**需额外确认**：D7、壳能力排期。

### 1.7 水源改卡走审批
- **改哪里**：消防站的新建/编辑/删除；支队的水源审批。
- **现状**：站级直写（`WaterServiceImpl.createWater/updateWater/deleteWater`），**零审批代码**；可复用模板=车辆审批（`ccds_vehicle_request` DDL `0001_vehicle_archive.sql:31-46` + `VehicleServiceImpl.submitRequest:160-192 / reviewRequest:221-246 / applyApprovedRequest:270-296` + 前端 `vehicles/index.js:270-351`）。模板有两个缺陷：`reviewed_at` 从不落库（`VehicleServiceImpl.java:238-243`）、已通过申请可被物理删除（`:266`）。
- **怎么改**：按统一审批模式新建 `ccds_water_request`（**必须补** `reason`、`from_status`、`to_status`、`reviewed_at`、`client_request_id` + 幂等唯一键 + `(station_id,status)`/`(status,reviewed_at)` 索引）：
  - 提交=站级本站（`requireRequestStation`）；审批=HQ/DEVELOPER（`requireReviewer`，大队不审批）。
  - 通过落档**单事务 + CAS**（`UPDATE ... SET status='approved' WHERE id=? AND status='pending'`，影响 0 行即已处理）：add→分配 `water_no` 后 insert；modify→覆盖原卡；delete→软删 + 写 `ccds_water_deleted`。驳回原卡不动。
  - 站级直写 create/update/delete 返回 403（提示「请提交审批申请」）；导入保留直写但必须过删除墓碑闸门（1.8）。
  - 站级列表可标「待审批」，统计仍只读正式表（天然成立）。
- **验收**：提交「在用→报修」通过前汇总逐字段不变；通过后该卡 repair、不好用 +1、from/to_status 与 reviewed_at 正确；驳回不变；站级直调 PUT 返回 403。
- **依赖**：1.1 / 1.2；1.6 依赖本项。**需额外确认**：与 ADR-0010「站级写、大队/支队只读」的语义张力（需记 ADR）。

### 1.8 删过的水源不能再被灌回来
- **改哪里**：水源同步、全市底表合并、导入。
- **现状**：软删靠改名绕唯一键（`WaterSourceMapper.xml:105-112`：`name = CONCAT(...,'#DEL#',id)`）→ **删除瞬间销毁编号**，无法按编号拒绝回流；无 `water_no`、无墓碑表、无 `retained`/`base_no`；`sync.js` 与水源零相关；全市接口直读 `selectAliveAll` 无闸门；导入只按 alive 同名去重（`WaterServiceImpl.java:334-338,373-376`）→ 删过再导入必复活。
- **怎么改（顺序不能反）**：
  1. 先补 `water_no` + `(station_id, water_no)` 唯一（历史回填：优先旧版 `municipal_xxx`，否则 `S{stationId}-{seq:04d}`）。
  2. 软删改为「先写 `ccds_water_deleted` 再软删」，**不再靠改 name 绕唯一键**。
  3. `ccds_water_base`（市政底表，`batch_no` + `confirmed`）+ `ccds_water_source.base_no`。
  4. 三入口（导入 / 底表合并 / 同步）统一走 `WaterCatalogGuard.shouldSkip()`。
  5. `retained=1` 的卡在 `getWaters` 前按**原 id、原编号**补回（un-delete，不换号）。
  6. 新明路以 `confirmed=1` 的批次替换。
  7. 导入时已删除编号即使出现在表里也不恢复，除非用户本次主动新建或审批通过。
- **验收**：删卡后导入 + 底表合并各一次仍不在列表且 `skippedDeleted≥1`；`retained` 卡被删后再打开 id/编号不变。
- **依赖**：无（先于 1.6）。**风险**：底表含全市坐标 → 接口限 HQ/DEVELOPER、日志只记批次数；**不要硬编码 `municipal_001` 这类旧编号**。

### 1.9 供水计算改用车辆档案
- **改哪里**：供水计算页（现在写着「一期无车辆档案」）。
- **现状**：参战车辆是 textarea 手填每行一辆（`supply/index.js:102-106`）；泵量纯前端正则写死 60/40（`water/shared.js:69-78`）；提示文案在 `supply/index.js:42-43`；车辆档案**无任何流量列**（`VehicleDO.java:70-85` 只有 waterCap/foamCap/powderCap/workHeight，且全是 String，如「18吨」）；水源流量用 nearby 的 `estimateFlow`（类型估算）求和（`supply/index.js:167`）。

## 四、人员和编组（4.1 – 4.5）

### 4.1 人员调动必须换新档案号
- **改哪里**：人员档案里的调动（现在没有调动入口）。
- **现状**：**本仓库无 `p_12` 概念**——主键是全局自增 `id`（`0001_roster.sql:2-24`，`ccds_profile` 无 `archive_no` 列）；**无调动入口、无接口**（`ApiPathConstant` 无 transfer/restore，`RosterController.java:68-240` 无调动）；无 `ccds_profile_transfer`；只有 `ProfileTombstoneDO`（墓碑，表已建 `0000_landing_tables.sql:6-29`，字段含 legacy_profile_id/archive_no/nfc/name_norm/source/三级 released_at），**唯一写入方是旧数据迁移**（`LegacyDataImportServiceImpl.java:810-850` 只把已批准的旧调动写成墓碑 `source=transfer_out`，不建新档、不搬站）。
- **怎么改**：先说明「换新号」在本仓库落地为 **`archive_no` 生成列**（`CONCAT('P', LPAD(id,8,'0'))` STORED + 唯一索引），或等价的应用层编号；调动**只允许 insert 新行**，严禁 `update` 源行 `station_id`、严禁复制 id/档案号；新增 `ccds_profile_transfer`（含 source_archive_no、merge_target_profile_id、client_request_id）；审批通过单事务：锁源 → 按 `name_norm` 查目标站 → 命中则要求「同名且显式指定并卡 id」、仅填空字段、**保留目标原档案号** → 未命中 insert（`phone_cipher` 直接复制密文，不解密）→ 源软删 + 写墓碑（`source='transfer_out'`）→ 申请置 approved。调出站按原档案号+人名删除，同步时不能因为他在调入站而回到调出站；调入站名单按姓名更新，**不能因为序号相同就换成另一个人**；恢复曾经丢过的调动档案时同样给新编号、不改调出站删除记录、不覆盖调入站原占号者。
- **验收**：南树园某人调到新明路 → 档案号不是原站内序号；新明路原占该序号的人还在；此人不再出现在南树园，再同步一次也不回去。
- **风险**：生产 464 人，`STORED` 生成列会触发表重建 → 需维护窗口；UI 需明示「档案号 P00000xxx」，与客户习惯的 p_12 不同。**依赖 4.2 墓碑**。

### 4.2 删除的人不能被同步加回来
- **改哪里**：人员删除 + 之后的同步/导入/花名册补人。
- **现状**：删除=确认后 `softDelete` + **清空 `nfc_tag`**（`RosterServiceImpl.java:161-172`、`ProfileMapper.xml:103-110`），**不写墓碑**；`ProfileTombstoneMapper` 只有 `selectByStationId/countByStation`（**无解封、无删除语句**），且仅被 `LegacyDataImportServiceImpl` 注入，`RosterServiceImpl` **完全没用**；导入只按 alive 姓名建索引（`RosterServiceImpl.java:310,340-354`）→ **删过的人必复活**。
- **怎么改**：
  1. `deleteProfile` 同事务「**先写墓碑再软删**」（软删会清 `nfc_tag`，墓碑是 NFC 唯一长期载体）；记档案号 + NFC（有则记）。
  2. 同步/合并/恢复丢档**禁止清除**这种按档案号或 NFC 记的删除记录；云端旧名单也不能把人加回。
  3. 只有用户自己主动保存、新建、导入、编组加人、绑定 NFC，才可以解开该人的删除记录。
  4. 按姓名误删的，**只允许解开姓名那一条**，不能把整张卡的档案号和 NFC 删除记录一起清掉。
  5. 花名册补人时见到已删除档案号就跳过（不能为「编制齐全」补回）。
  6. 发布或同步出去之前再滤一次已删除人员（导出/值班快照/编组导出/指挥端下发统一过 `TombstoneGuard`）。
- **验收**：删一人后用仍含他的旧花名册同步，列表仍无他；再在本站导入或新建主动加他，可以回来。
- **风险**：墓碑长期有效会阻止「同名新人」导入 → 必须给「已删除人员」列表与显式恢复入口，否则现场会误判导入失败；旧数据无墓碑（无法回溯历史删除）。

### 4.3 战斗编组按槽位删除，固定编制卡不能被占
- **改哪里**：人员档案里的战斗编组。
- **现状**：`BattleGroupDO` 只有 id/stationId/name/sortNo；保存是**全删全插**（`RosterServiceImpl.replaceGroups:461`）→ **组 id 每次保存都变**，无法用 id 做删除键；无固定编制卡、无槽位、无编组墓碑。
- **怎么改**：
  1. `ccds_battle_group` 增 `slot_no`（固定 1/2/3）+ `is_fixed` + 唯一 `(station_id, slot_no)`；每站保留固定指挥员/安全员/通信员编制卡，作战组不得使用这三张固定编号。
  2. 若作战组用了安全员/通信员编号且名单与编制卡完全一致 → 丢掉作战组外壳，留下编制卡。
  3. `replaceGroups` 全删全插改**按 id/name 增量更新**。
