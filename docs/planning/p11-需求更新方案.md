# CCDS《ccds 安装包改法明细》需求更新方案（v1.0）

- **需求来源**：客户《ccds 安装包改法明细》（对照现网 8.98 / 版本号 6358），25 个条目，含 6 节施工顺序与 7 节整包验收。
- **代码基线**：本仓库当前工作树（v0.1.1；`app-h5` H5 + `ccds-*` Java 分层后端；工作树含水源/文件/重点单位未提交改动）。
- **比对样本偏差（必须先纠正）**：`tmp_apk` 内置的是 **8.76 / 版本号 6336**（`assets/index.html` 内 `APP_VERSION_NAME`/`APP_VERSION_CODE`），不是 8.98/6358。故 `tmp_apk` 只能作字段与逻辑参照，不能作为"现网 8.98 行为"的证据；客户文档中"现在：……"描述的界面与本仓库现状多数一致，说明客户是照"手上 APK 看到的界面"写的。
- **本文性质**：勘察与实施方案，不含代码改动。所有"现状"均已落到 `文件:行` 核对；标「待确认」处需客户或技术负责人拍板。

### 1.2 三个判断（决定本项目怎么排）

1. **这不是一次"改改界面"的迭代。** 25 项里有 **9 项是对一期明确放弃项的重新解禁**（A-04 审批、A-07 作业模式、X-01 汇总表、X-02 视频审核、R-03 保留清单、A-03/ADR-0012 车辆泵量、A-01 现场态位置的近似项、X-03 版本、5.1 首登改密红线）。若不先补 ADR 与规格，实现即"违反仓库已生效架构决策"，后续 review 会被判不合格。
2. **工作量 55% 压在水源域（1.x ≈ 76 人日）。** 根因是 `ccds_water_source` 只有 8 列，客户要的是一套完整的"市政水源台账 + 检查 + 审批 + 统计"；且导入是当前**唯一**数据入口（现库水源 0 条），1.4 做不好等于整个水源模块没有数据。
3. **有 6 个"半成品"能省 30% 工时**：`ccds_attack_archive.mode`（列已建）、`main-pager` 双页骨架、`ccds_org_tree`（后端已返回大队树）、`ccds_vehicle_request`（审批模板）、`HazmatSearchClient` + `ModelGateway.completeVision`（外呼与视觉网关）、`SensitiveMaskUtil`（脱敏唯一实现）。方案一律"补半成品"优先，不重写。

## 三、横切设计（先定 5 个共用机制，省 30% 工作量）

### 3.1 变更审批域（服务 1.7、4.1，未来复用）

现状：只有 `ccds_vehicle_request` 一套审批（`0001_vehicle_archive.sql:31-46` + `VehicleServiceImpl.submitRequest/reviewRequest/applyApprovedRequest` + `pages/vehicles` 审批 UI）。它**不能原样搬**，缺两个硬字段。

统一设计：不建"通用审批表"（各域字段差异大、JOIN 复杂），而是**统一模式 + 统一状态机 + 统一前端组件**：

```
ccds_{water|profile}_request
  id, station_id, action(add|modify|delete|transfer),
  item_json, before_json, from_status, to_status,
  reason(申请原因，必填), status(pending|approved|rejected),
  review_reason, created_by, reviewed_by, reviewer_name,
  reviewed_at, client_request_id, gmt_create, gmt_modified
  UNIQUE (station_id, client_request_id)   -- 提交幂等
  KEY (station_id, status), KEY (status, reviewed_at)  -- 列表与"本月维修数"统计
```

- 权限二分：提交=`requireRequestStation`（本站站级）；审批=`requireReviewer`（HQ/DEVELOPER，大队不审批）。
- 审批落档必须单事务、CAS 状态（`UPDATE ... SET status='approved' WHERE id=? AND status='pending'`），影响 0 行即已处理。
- **修掉模板的两个缺陷**：① `reviewed_at` 在 `VehicleRequestMapper.xml:25-33` 没落；② 已通过申请可被物理删除 → 审批表一律禁止删，只允许"撤回 pending"。
- 站级直写收口：`create/update/delete` 对站级返回 `*_WRITE_FORBIDDEN`（提示"请提交审批申请"）；导入保留直写但必须过删除墓碑闸门（见 3.2）。

### 3.2 删除墓碑与目录合并闸门（服务 1.8、4.1、4.2、4.3）

现状：水源与人员都是**软删**，但软删方式不同，且都**没有墓碑**：
- 水源：`softDelete` 把 `name` 改成 `#DEL#{id}` —— 删除瞬间**销毁编号**，无法按编号拒绝回流（`WaterSourceMapper.xml:105-112`）。
- 人员：置 `deleted_at` 并**清空 `nfc_tag`**（`ProfileMapper.xml:103-110`）—— 删除后无法按 NFC 记忆；导入只按 alive 姓名匹配，**必然复活**（`RosterServiceImpl.java:310,340-354`）。
- 编组：保存是"全删全插"（`replaceGroups`），组 id 每次保存都变，无法用 id 做删除键。

统一设计（三张墓碑表，键各自定义，语义统一）：

| 表 | 唯一键 | 记录 | 解开条件 |
|---|---|---|---|
| `ccds_water_deleted` | `(station_id, water_no)` | 水源编号/名称/类型/删除来源/manual 或 approval | 用户主动新建、审批通过新增 |
| `ccds_profile_tombstone` | `(station_id, profile_id)`、`(station_id, nfc_alive)` | 档案号/NFC/姓名归一/来源 `user_delete` 或 `transfer_out` | 姓名、NFC、档案号**分级**解开（默认只解姓名，NFC 需 `confirmNfc`，档案号永久） |
| `ccds_battle_group_tombstone` | `(station_id, name_alive)` + `slot_no` | 组名归一/slot/来源 `user_delete` 或 `legacy_bug` | 用户重新新建同名组；`legacy_bug` 可由清理任务精确匹配解开 |

三条铁律（对应客户开篇三条底线）：
1. **墓碑只增不删**：任何同步/合并/恢复/导入路径禁止清墓碑；清理方法按表隔离（清编组墓碑不得触碰人员墓碑）。
2. **优先级**：用户显式操作 > 墓碑 > 现存 alive 档案 > 目录/底表/Excel 旧数据。
3. **发布前再滤一次**：导出、值班快照、编组导出、指挥端下发，统一过 `TombstoneGuard`。

### 3.3 作业模式与阈值下发的单一事实源（服务 2.2、2.3、3.1、3.3）

现状三处割裂：
- 可见条件硬编码两处：后端 `AttackServiceImpl.listSnapshots` → `hasUnwithdrawn`（含 `pendingCount`）、前端 `hq/index.js visibleRows()` → `snapshotActiveCount`（同样含 pending）。
- 阈值三套：站端本机 `localStorage`（`stores/settings.js`）→ 服务端硬编码 `AttackRuleConstant`（`ScbaEstimateServiceImpl.resolveStatus`）→ 指挥端又用**指挥设备本机**值重算（`hq/station.js` + `board.js`）。
- 模式：`ccds_attack_archive.mode` 列已建但从不赋值；站级无模式状态；`AttackSnapshotVO` 无 `workMode`/`thresholds`。

统一设计：
- **模式存独立表**，不塞快照表（`ccds_station_snapshot` 是派生表，整行 upsert 会互相踩）：`ccds_station_work_mode(station_id PK, work_mode test|training|dispatch, updated_by, gmt_*)`；变更走 `PUT /stations/{id}/work-mode`，复用现有 `refreshSnapshot → publishAfterCommit` 链路即时下发。
- **阈值存站级表**：`ccds_station_scba_setting(station_id PK, warn_pressure, danger_pressure, warn_time_min, danger_time_min, default_work_level, voice_enabled, updated_by, gmt_*)`；`ScbaEstimateService.resolveStatus` 增 `Thresholds` 参数（`AttackRuleConstant` 降级为"未配置站的默认值"）。
- **快照扩展**：`AttackSnapshotVO` 增 `workMode` + `thresholds`（纯新增字段，旧端忽略）。
- **判定归服务端**：前端只渲染服务端下发的 `status`，本机阈值仅用于离线倒计时展示；共享页与指挥端不再各自重算。
- **可见性单点**：`workMode=='dispatch' && (in+warn+danger) > 0`（**去掉 pending**），后端过滤 + 前端兜底同一表达式；增量拉取分支（`modifiedSince`）**不得**过滤，否则离线站永远补不回来。

### 3.4 统计口径与聚合服务（服务 1.2、1.6、1.9）

原则：**一个谓词、一条聚合 SQL、一份 VO、导出与屏幕同源**。

```sql
-- 好用/不好用（唯一谓词，落到 WaterStatusResolver，前端与导出都调它）
bad := status='repair' OR usable='bad' OR is_repair=1
good := status='active' AND usable IS DISTINCT FROM 'bad'
-- 注意：绝不允许"reason_text 非空"参与判定（旧原因文本不得计入）
```

- 汇总一次聚合（禁止每单位子查询）：
  `GROUP BY station_id` 取 `SUM(type='crane')`、`SUM(type='crane' AND status='active')`… 三路结果（水源聚合 / 九原因分布 / 视频数 / 本月维修数）在 Service 层内存拼装。
- 不变量（可直接写断言）：`good + bad = total`；`Σ9原因 = bad`；`地上 + 地下 = 消火栓总数`；三张类型表中"总数=0 且本月维修数=0"的单位不输出。
- 导出：`SpreadsheetCodec` 现只生成单 sheet（`writeXlsx` 固定 `sheet1.xml`）→ **新增** `writeXlsxMultiSheet`（不动现有方法），统计导出与屏幕共用同一 `WaterStatsVO`。
- 权限修正（顺手修现有越权）：`listCityWaters` 只 `requireAccount`，大队能看到全市 → 改用 `OrgQueryService.listVisibleStationEntities()`。

### 3.5 媒体采集与 AI 审核能力（服务 1.5、5.4）

技术事实（不是实现细节，直接决定能不能做）：
- **服务端无媒体库**（`pom.xml` 无 ffmpeg/javacv），且 `AGENTS.md` 红线禁止 `Runtime.exec` → **10 秒校验与三帧抽取只能在客户端（壳/H5）完成**；服务端只能采信客户端上报，`check_status` 不能当"确证出水"。
- **壳能力缺口**：H5 桥能力集只有 `nfc/locate/heading/speak/alarm/vibrate/openUrl`；Android `MainActivity` 未覆写 `onShowFileChooser`（`<input type=file>` 在 WebView 内不工作），`pickFile()` 只有 `ACTION_GET_CONTENT`（不能拍照），Manifest 无 `CAMERA`；鸿蒙桥全部 `UNSUPPORTED`。
- **可用底座**：COS 预签名三步上传（`api/files.js`）、`ModelGateway.completeVision`、`AssistRuleConstant.IMAGE_BASE64_MAX_LENGTH`。

设计：
- 新增 `capturePhoto` / `recordVideo(EXTRA_DURATION_LIMIT=10)` / `probeVideo`（`MediaMetadataRetriever` 读时长 + 抽 0/50%/100% 三帧）；H5 加 `lib/media.js`（`loadedmetadata` + canvas 兜底）；鸿蒙先降级"不支持拍摄，请从相册选择"。
- 服务端：`ccds_water_video`（`water_id/file_id/duration_ms/frame_file_ids/check_status/check_reason`）+ `ModelGateway.completeVision` 逐帧判定；图片/视频走**私有桶 + 短时预签名**，禁公开 URL。
- 列表性能：照片封面必须**批量取**（一次 `selectByBizTypesAndIds` + 批量预签名），并下线列表路径上的逐文件 COS HEAD 校验。

## 四、分项方案（按文档编号）

> 每项固定四段：**改法要点 / 数据变更 / 风险 / 验收**。行号以勘察时工作树为准。

### 1.1 水源卡片补全字段
- **改法**：`ccds_water_source` 新增 17 列（`setup/pipe_diameter/pressure_mpa/flow_lps/supply_form/add_height_m/usable/reason_code/reason_text/part_code/is_repair/drain_valve×4/has_warmth_measure/no_warmth_reason`），全部可空以保回滚；`WaterSaveCommand`/`WaterVO`/`WaterSourceDO`/`WaterSourceMapper.xml`（resultMap、WaterColumns、insert、insertBatch、update **五处**同步）；`WaterViewTranslator` 出 `bad` 与各 `*Label`；编辑表单按顺序插入 6 个属性控件 + 9 项原因单选 + 8 项部件单选 + 可使用/是否报修；列表卡片（`water/index.js:386-438`）在名称下加"原因 · 部件 · 备注"行。

- **改法**：①`ccds_battle_group` 增 `slot_no`（固定 1/2/3）+ `is_fixed` + 唯一 `(station_id,slot_no)`；②`replaceGroups` 全删全插改为**按 id/name 增量更新**（现组 id 每次保存都变，无法做删除键）；③新表 `ccds_battle_group_tombstone`，只记 `(组名归一, slot_no)` 精确值，**禁止**旧版 `slot:fire:N` 类通配键；④删组前写墓碑，`source` 区分 `user_delete/legacy_bug`，只有 `legacy_bug` 可自动清理；⑤折壳规则：作战组 `slotNo` 与固定卡冲突且成员集合完全一致 → 丢外壳留固定卡，否则 `GROUP_SLOT_RESERVED`；⑥固定卡永不删（payload 缺省时从旧值恢复）。
- **风险**：组 id 稳定化会改变前端缓存与值班快照引用（快照存 name，风险低）；固定卡注入会让 roster/值班/导出多处多 3 张卡 → 需同步调整；固定卡**名称**需客户定（指挥员/指挥组、安全员/专职安全员、通信员/通讯员）。
- **验收**：删"灭火1组"→"灭火救援1组" id 与成员不变、墓碑键为精确组名；删"灭火救援5组"后导入不复活；每站固定卡 3 张且删固定卡返回 `GROUP_FIXED_FORBIDDEN`；清理组墓碑后人员墓碑行数不变。

### 4.4 值班表能改当天和明天编组
- **改法**：`ccds_duty_day` 增 `vehicle_snapshot_json`；`DutyDayDTO` 增 `vehicleSnapshotJson/groupSnapshotMode(preserve|replace)/keepOfficers`；服务端**按日期硬校验**：仅今天/明天且 `replace` 才写编组与车辆，历史日只更主官/副职/备注并强制 `preserve`；`keepOfficers=true` 保留原值（修掉 `updateById` 整行写空的隐患）；前端可编辑日渲染编组编辑器（操作本地 `state.dutyGroups`）+ 车辆选择器；新增 `GET /duty/battle-groups/export`（HQ，各站最新快照，无则回退当前 roster）与 `GET /profiles/export-all`（HQ）；站级仍只导本站。
- **风险**：旧客户端不传新字段 → 服务端默认 `preserve` 兜底；历史日期不再被覆盖属**行为修复**但会改变旧端感知；全量导出 464 人需分页/流式；导出是否含电话需与 4.5 口径一致。
- **验收**：今天调组保存后另一设备可见；上月某日保存只改备注时 `group_snapshot_json` 哈希不变；`keepOfficers` 时主官/副职非 NULL；支队导出前后各站 `gmt_modified` 不变（只读）；站级请求全量导出 403。

### 4.5 档案显示完整电话
- **改法**：把"是否返回明文"从 `writable` 拆出为 `canViewPhone`（站级本站/大队下属/支队/开发者全部），`getRoster/getProfile` 用它作 `exposePhone`；`ProfileVO` 增 `phoneVisible`；前端两处（`roster/index.js:175`、`roster/edit.js:73`）改为 `prof.phone || prof.phoneMasked`；响应加 `Cache-Control: no-store`；日志继续 `@ToString.Exclude`。
- **风险**：**扩大敏感数据暴露面**，需客户书面确认；共享页仍不得出现电话/NFC/账号（现有 `ShareAttackVO` 投影已保证）；旧 APK 直连 API 同样拿到明文 → 终端可信性待确认。
- **验收**：站级/大队/支队在本站及其可见站看到完整 11 位并 `phoneVisible=true`；不可见站 403；`/s/{token}` JSON 与 DOM 均无电话字段。

### 5.1 固定账号直接登录（安全例外）
- **改法**：前端删三道门（`app.js:150/159/173-176`、`login/index.js` 的 `mustChange` 分支），三句说明常显；后端**保留** `MustChangePasswordInterceptor` 与改密接口（管理员重置兜底），只把 `is_must_change_password` 数据 patch 置 0；新增设置页「修改密码」入口（承接原 `api/auth.js:changePassword`，仍校验 ≥8 位）；新增离线工具按账号生成初始口令 BCrypt（输出 SQL，明文不入库不入仓，42 账号）。
- **安全评估（必读）**：账号清单=单位首拼（种子文件即公开映射），口令=账号+固定后缀 `119`（旧 APK 常量可直接反编取得）→ 攻击者可**零成本枚举全部 42 账号**，且支队账号可见全市、大队可见下属全部站，等于一个后缀击穿三级隔离；相较"单一种子口令"实为**熵下降**。缓解建议：①支队/开发者不用 `+119`，改一次性随机口令清单；②若客户坚持，首登弹一次改密引导、保留失败 5 次锁 10 分钟、登录审计留存 ≥6 个月、口令仅 HTTPS 下发；③保留改密能力与最小长度 8 位。
- **验收**：新账号登录无改密页直接进对应首页；大队只见下属站；支队见全部；设置页可改密且 <8 位被拒；人工置 `must_change_password=1` 仍被拦截器拦住。

### 5.2 版本页检查更新与教程（边界：X-03）
- **改法**：去"一期"字样，显示名称/版本名/版本编号；新增 `GET /app/version`（后端配置驱动，替代旧版 R2 直连清单）返回 `versionName/versionCode/releaseNotes/updatePageUrl/installGuideUrl/operationGuideUrl/force`；前端以 `versionCode` 比对，弹窗三按钮（打开更新页 / 稍后 / 忽略本版，忽略按账号按版本记录）；新增内置教程页 `#/guide/install`、`#/guide/operation`（离线可看）；版本页可再次打开免责声明（放开 `#/legal?view=1`）。**必须先统一版本号三源**（`package.json` 0.1.0 / Gradle 0.1.1+code2 / 鸿蒙 0.1.0+code1 且桥内硬编码）。
- **边界**：只做"检查更新 + 打开更新页 + 人工安装"，**不做**应用商店、静默/自动安装、后台替换（X-03）；APK 与更新页放 COS 私有桶，后端签短时 URL（X-04：禁前端配置云端地址）。
- **风险**：鸿蒙 `openUrl` 未实现 → 教程/更新页"点了没反应"是硬缺口，需补壳；`usesCleartextTraffic=false` → 更新页必须 https；不自动安装须在文案写明；教程文案仓库内**零副本**，需客户提供旧版两份 HTML。
- **验收**：版本页 grep"一期"零命中；同版本显示"已是最新"；更高 versionCode 弹三按钮；忽略后不再弹；两教程离线可开；断网显示"检查更新失败"不白屏。

### 5.3 危化品登记库检索
- **改法**：四层降级——①登记库（新增 `HazmatRegistryClient`，配置 `registry-url/app-key/timeout`，`HttpClient` + 3 次重试，风格照现有 `HazmatSearchClientImpl`）→ ②落库 `ccds_hazmat_entry`（服务端本机备用库，可运营）→ ③现有 8 条内置常量 → ④H5 离线库（≥20 条，含 UN1005 液氨）；`HazmatSearchClientImpl` 改为编排器，`HazmatServiceImpl` 不再整体抛错，DTO 增 `source(registry|local|builtin)` 与 `degraded`；页面文案改「危化品名称 / UN编号 / CAS号」+ 示例，按钮「云端数据库搜索」，未命中引导文字研判，降级显示"已改用备用库"，结果固定尾注"以现场侦检、运输单据、安全技术说明书和登记信息为准；认不准请说明不确定"。
- **风险**：登记库**数据使用授权/转载合规**须书面确认；登记库是否有可对接 API 与凭据未知（无 API 则只能"本地库 + 定期导数据"）；视觉模型默认 `qwen-plus` 非视觉，未换模型则拍照研判不可用（与 5.4 同修）。
- **验收**：`UN1005` 出液氨（名称/危险性/应急处置）；上游不可达→本地库+"已改用备用库"；飞行模式→离线库+"本机备用库（离线）"，无匹配给明确失败说明；任何结果含固定尾注。

### 5.4 AI 对话可拍照
- **改法**：问答区加「拍照」「选图」两个 input + 缩略图；抽 `lib/image.js`（`fileToBase64` + 压缩到 ~1.5MB，长边 1600/quality 0.8），危化品页改为复用同一实现；请求体加 `imageBase64/imageContentType`；后端 `ChatCommand` 加两字段，`ChatServiceImpl` 有图走 `completeVision`、无图仍 `completeText`（文本零回归）；把 `HazmatServiceImpl.validateImage/stripDataUrl` 抽成 `AssistImageValidator` 两处共用；`ModelProperties` 加 `visionModelName`（默认 `qwen-vl-plus` 类），`application.yml` 加 `CCDS_MODEL_VISION_NAME`。
- **结论**：图片 **base64 直传本后端**，不进 COS、不前端直连模型厂商（F11/ADR-0009 同口径）；两处拍照入口**不合并**（AI=问答附图，危化品=物质识别），文案区分。
- **风险**：峰值 2MB/次 → 必须前端压缩；照片会发第三方模型厂商 → 界面提示"请勿上传含人脸或涉密标识的照片"；不落库即无留痕（若有留痕需求另立）。
- **验收**：AI 页拍照+提问直接出结果（不跳危化品页）；5MB 图自动压缩或提示超限且不发请求；只发图/只发文字均 500 以下；危化品拍照独立可用；断网提示"无网：已禁用 AI"；日志无 Base64。

### 5.5 重点单位完整电话
- **改法**：`DutyAccessServiceImpl` 新增 `canReadPlainPhone`（站级本站/所属大队/支队/开发者可见），`KeyUnitServiceImpl` 两处 `isWritable` 换它（创建/更新返回值仍 true，写权限不变），`phoneMasked` 保留给未来共享/导出；前端 1 行回退 `unit.phone || unit.phoneMasked`（顺带修"非站级详情页电话空白"）。
- **风险**：与"电话仅站级明文"惯例不同 → 在 `harness/04-security.md` 记例外：重点单位联系电话对可见角色明文，**不得进共享页/导出/日志**；建议响应加 `no-store`。
- **验收**：站级/大队/支队列表与详情电话与档案一致无星号；非所属大队仍 `DUTY_STATION_FORBIDDEN`；`/s/{token}` 无 phone；预案/平面图上传删除回归一致。
