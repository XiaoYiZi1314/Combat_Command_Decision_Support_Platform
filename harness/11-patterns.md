# 11 · 模式、重构与依赖注入

适用：重构、引入设计模式、提高可测试性。模式是手段，禁止为用而用。

## 模式

初期能简单实现就简单实现，靠持续重构演进。

重点掌握：单例、工厂、建造者；代理、装饰器、适配器；观察者、模板、策略、职责链、迭代器、状态。

其余了解即可。典型用途：

| 模式 | 场景 |
|------|------|
| 单例 | 配置、连接池（优先交给 Spring 单例） |
| 工厂 | 创建逻辑复杂，创建与使用解耦 |
| 建造者 | 多必填/可选字段的复杂对象 |
| 代理 | 鉴权、限流、事务、审计 |
| 装饰器 | 功能叠加 |
| 适配器 | 外部接口与本系统不一致 |
| 观察者 | 事件通知 |
| 模板 | 固定流程 + 扩展点 |
| 策略 | 去掉长 if/switch |
| 职责链 | 过滤器、审批 |
| 状态 | 流程 / 状态机 |

## 重构

重构是日常的一部分。没有测试的大规模重构先补测或拆小。

- 小重构：重命名、提炼函数、去魔法数字（可随时做）。
- 大重构：拆模块、加抽象层（须用户同意，见 AGENTS.md 第 6 节）。

时机：坏味道、设计不再适配需求、加功能前整理周边。

## 依赖注入

禁止在类内部 `new` 业务依赖。通过构造器注入接口（`@RequiredArgsConstructor` + `final`）。单测用 Mock 替换实现。

## 对照

设计：SRP / OCP / DIP / DRY / KISS / YAGNI / LOD。

代码：参数不过多、嵌套不深、命名达意、无魔法数、公共 API 有注释、函数不太长、用了 DI。

模式：是否真需要？扩展性是否真提高？有没有过度设计？
